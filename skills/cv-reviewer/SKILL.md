# cv-reviewer

先判断候选人处于什么阶段、材料是什么形态，再决定简历应该扩展、压缩、编排还是精确去重。不要对所有候选人机械套用同一套“大厂简历”标准。

## 读取参考

1. 始终完整阅读 [references/methodology.md](references/methodology.md)。
2. 始终完整阅读 [references/candidate-routing.md](references/candidate-routing.md)，完成候选人档次与材料形态路由。
3. 始终完整阅读 [references/audit-rubric.md](references/audit-rubric.md)，使用对应档次的量表。
4. 按目标行业和岗位选择术语库，完整阅读选中的文件：
   - 商业、市场、销售、战略、财务、HR、内容： [references/lexicon-business.md](references/lexicon-business.md)
   - 产品、用户研究、数据、AI、工程、设计： [references/lexicon-product-tech.md](references/lexicon-product-tech.md)
   - 项目运营、供应链、制造、教育、医疗、法律、公共与科研： [references/lexicon-sector.md](references/lexicon-sector.md)
5. 输出前完整阅读 [references/output-template.md](references/output-template.md)。

只加载与当前目标相关的术语库；跨行业时读取来源行业和目标岗位所在术语库，用业务含义建立翻译映射。

目标行业未被术语库覆盖时，不套用最相近行业的黑话。改用 JD、公司产品说明、候选人素材和可核对的行业标准，临时提取 `业务对象｜核心问题｜典型动作｜交付物｜指标｜约束` 六类词，建立本次任务专用术语表。

## 输入与来源

接收当前简历，以及可选的 JD、旧版简历、经历素材、作品集、项目说明和修改建议。冲突时按以下优先级处理：用户本轮说明 → 当前事实素材 → 当前简历 → JD → 旧版或建议稿。

为每段材料建立内部经历卡：

`背景/问题｜对象/用户｜角色范围｜约束/难点｜动作｜工具链/方法｜交付物｜结果/外部验证｜可追问 Hook｜目标岗位相关性`

不同经历的事实不得拼接成一个项目。没有正式实习不等于没有证据；课程、校园组织、比赛、志愿、自由职业、个人项目和作品均可进入素材池。

## 第一步：双轴分类

### 候选人档次

根据证据强度、责任范围、成长连续性与目标竞争阶段分类，不只按经历数量或公司名：

- `起步型`：正式履历少，主要依靠校园、课程、个人项目、简单实习或可迁移能力。
- `成长型`：已有多段大小不同的履历，角色范围、业务难度、Title、结果或平台信号呈现成长路径。
- `冲刺型`：拥有多段平行重要的高信号履历，当前任务是围绕明确岗位进行取舍、去重和精确命中。

若介于两档之间，选择较低档作为内容门槛、较高档作为发展建议，并写明判断依据。

### 材料形态

分别判断：

- 履历总量：`过少 / 适中 / 过多`；
- 单条密度：`单薄 / 适中 / 丰富 / 混合`。

总量和单条密度独立判断。履历很多但每段都薄，不能按冲刺型处理；只有一段但信息丰富，也不能强行拆成许多平行经历。具体路由见 [references/candidate-routing.md](references/candidate-routing.md)。

## 第二步：确定叙事与证据路线

### 起步型

- 选定一个可被现有材料支持的候选人叙事，不把“没有实习”写成缺陷清单。
- 用 `兴趣/特质 → 主动行动 → 作品或外部反馈 → 下一步岗位` 建立最短证据链。
- 把校园、课程和个人项目翻译成岗位可识别的问题、工具链与结果；不假装企业职责。
- 保留一个与岗位相关的个性锚点，使候选人有记忆点但不脱离招聘规范。

### 成长型

- 识别成长主线：问题复杂度、负责范围、协作对象、平台级别、结果责任或专业深度如何逐段增加。
- 围绕目标叙事编排“进入领域 → 掌握职能 → 承担更大范围 → 接近目标岗位”的养成路线。
- 允许为展示成长而不完全按时间或品牌排序，但最相关和最高信号经历仍应靠前，并说明排序逻辑。
- 删除只重复旧能力、不能贡献成长节点的经历。

### 冲刺型

- 先定义目标岗位的核心业务问题，再从多段高信号履历中选择最强证据。
- 保持高标准化：顶部能力自述、相关履历前置、相似生态位去重、跨行业避重就轻、底部补充能力点。
- 每段保留经历强制使用两层“总—分”，并给外行可懂的背景、前置条件、因果链和可追问 Hook。
- 不靠经历数量取胜；保留能形成互补证据的 3–5 段主经历，其余压缩或删除。

## 第三步：适配履历容量与单条深度

- `过少 + 单薄`：先做证据挖掘与补问；每段至少形成“问题 + 关键动作/工具链 + 可观察结果”，不强凑 3–4 个分点。
- `过少 + 丰富`：把最强一两段写成支柱案例，用能力区和作品链接补广度，不拆成虚假的多段履历。
- `过多 + 单薄`：按目标能力聚类，删除同生态位重复项；必要时合并同一组织内真实连续项目。
- `过多 + 丰富`：建立证据优先级；前三段详细、支持段压缩、低相关段删除，避免每段都写满。
- `混合`：给每段分别标记 `支柱 / 证明 / 补充 / 删除`，按角色采用不同展开深度。

不要用固定字数代替判断。篇幅分配服从“目标岗位需要什么证据”和“这段经历能贡献什么新信息”。

## 第四步：写出专业性与个性

### 专业结构

对起步型与成长型，重点检查：

`问题/前置条件 → 使用的工具链、方法与关键动作 → 结果、交付或外部反馈`

工具链可以是软件、分析框架、协作机制、实验流程、研究方法或行业流程，但必须与准确动词、对象和交付连写。

对冲刺型，每段必须有：

1. 第一层总述：背景/业务、对象、角色目标、主要能力模块、总体结果；
2. 第二层分述：每个能力点先写问题与前置条件，再写取舍、动作链、方法/工具、结果与影响。

总述保持通俗，分述体现行业专业性。陌生行业、产品、机构、缩写和业务模型先翻译成人话。

### 个性锚点

个性必须通过选择、判断或长期行动体现，而不是堆形容词。只保留同时满足以下条件的内容：

- 与目标岗位、行业用户或工作方式相关；
- 有作品、持续行为、方法偏好或外部反馈支撑；
- HR 五秒能理解，不替代专业能力；
- 能形成记忆点，但不让候选人脱离岗位常规评价框架。

## 第五步：建立因果与追问 Hook

每段支柱经历检查：为什么要做 → 面临什么约束 → 为什么选这套方法 → 如何推进 → 结果如何改变下一步。不要只列动作。

保留 1–2 个可追问 Hook，例如关键取舍、异常结果、跨部门冲突、失败后的调整、指标口径或尚未显性的业务洞察。Hook 必须有可讲内容，不是故意留下事实漏洞。

## 第六步：Title、时间与跨行业呈现

- 对平淡 Title，可在相邻职能内给功能化建议，并保留 `原写法 → 建议写法 → 解决的问题 → 风险`。
- 对过短经历，可比较删除弱段、只强化一段、合并真实连续项目、调整月份呈现、突出项目周期或并行背景。
- 跨行业时保留可迁移的问题类型、方法和结果，压缩来源行业黑话；用目标行业术语库翻译，不能把目标 JD 职责倒写成既往事实。
- 可以直接提出 Title 与月份建议稿，但建议稿不是已核验事实；统一由用户手动修正。

## 第七步：生成经历精修交接包

审查报告必须包含 `接轨 cv-experience-refinement`。该部分只决定“改哪段、为什么改、用什么证据和主题改”，不在审查 Skill 内重复完成深度文案改写。

按以下规则路由：

- `支柱 / 证明`：进入精修候选列表，按目标岗位价值与 P0/P1 优先级排序；
- `补充`：默认保持一行或轻量修改，不送入深度精修，除非它承担独立证明任务；
- `删除`：不得送入精修，也不得因文案可优化而改变删除结论。

为首批处理经历写出：处理范围、下游模式、工作概述目标、2–4 个能力主题、可用事实、待确认项和禁止补写内容。下游模式必须使用 `cv-experience-refinement` 的原生含义：

- `final`：动作、方法、交付与结果均有来源支持，只需组织表达；
- `enhanced-draft`：至少能识别两个动作/方面，但方法、工具、数据或结果细节不完整，可生成带统一事实核对提示的增补草稿；
- `incomplete`：服务对象或持续动作不足，无法划出至少两个方面，先补充素材再改写。

建议 Title、月份、排序、目标 JD 用语和审查推断不得混入“可用事实”。不同经历的事实继续隔离；下游 Skill 只调整单段内容与段内主题顺序，不替代本报告的跨经历取舍和整体编排。

用户只要求审查时，输出交接包和一段可复制的调用语句后停止，不修改源文件。用户明确要求“审查后继续改写/精修”时，先完成审查，再调用或读取 `cv-experience-refinement`，按交接包处理首批范围：

1. 只传递当前来源能支持的经历卡、目标 JD 语言和待确认项；
2. 使用交接包指定的 `final / enhanced-draft / incomplete` 模式；
3. 保留机构、角色、日期和经历归属，不跨项目拼接；
4. 精修完成后重新核对审查报告中的叙事、证明任务和禁写边界。

若环境中没有 `cv-experience-refinement`，不要假装已调用；保留完整交接包，并说明需先安装该 Skill 或将调用语句交给支持它的 Agent。

## 第八步：文档与输出

输入为 PDF/DOCX 时，完整提取文本并渲染全部页面。文本结论和版面结论分开；渲染器缺失中文字体时说明限制，不把预览方框误判为源文件缺字。

只要求审查时不修改源文件。要求改写时，先完成档次、叙事、取舍、容量规划和精修交接，再改写保留经历。

严格使用 [references/output-template.md](references/output-template.md)。生成文件后运行：

```bash
python3 scripts/validate_audit.py audit.md
```

最终输出最后一行必须逐字为：

`> 结果仅供参考，需要手动修正`
