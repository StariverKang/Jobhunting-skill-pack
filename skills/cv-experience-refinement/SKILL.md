# CV Experience Refinement

默认输出中文深度材料版：先用无第一人称的工作概述说明业务、范围和目标，再以 2–4 个对应的能力主题展开行动链。用户明确要求时，才压缩为一页简历版。

## 输入与范围

接收履历/项目文本或文件、处理范围（全部或指定段落），以及可选 JD。全量处理时保持原经历顺序；指定段落时只处理该段。保留已给出的机构、角色、日期和经历归属，不合并不同经历的事实。

JD 只用于选择能力主题、行业语言和排序，不能把 JD 职责写成既往经历。

## 读取参考与建立素材卡

1. 完整阅读 [references/structure.md](references/structure.md)。
2. 需要校准句长、层级或信息不足写法时，阅读 [references/examples.md](references/examples.md)。
3. 只按经历所属行业选读 [references/lexicon.md](references/lexicon.md) 的对应小节；术语必须能接上具体动作、对象或交付物。
4. 对每段经历整理内部素材卡：`业务/对象｜角色或位置｜职责范围｜动作与方面｜目标或卡点｜方法/工具｜数据/成果｜原工作概述长度`。素材只能留在本段，不跨项目拼接。

## 起草流程

1. **先判断硬性信息缺口。** 能从材料中识别至少两个可解释的动作/方面（例如“需求梳理 + 上线推进”“内容生产 + 数据复盘”）时，直接起草。数字、方法论、工具、交付和成果不完整时也不要中断。
2. **只有动作/方面不足才追问。** 若无法确定服务对象、持续负责的动作，或无法划出至少两个方面，输出 `### 缺失的动作/方面`，逐条列出缺什么并请用户补充；不要用“协助运营”硬凑出完整闭环。
3. **写第一层“总”。** 用 `工作概述` 写 1–2 句，不用“我/本人”。优先以“参与、负责、围绕、推进、统筹、面向”等动词开头，或直接罗列工作范围与动作目的；说明业务是什么、覆盖什么工作、服务谁或解决什么问题。若源履历已有概述，新概述的可见字符数不得低于原概述；若没有，至少 80 个可见字符。
4. **划出第一层“分”。** 将素材归为 2–4 个互不重复的能力主题。主题标题就是第一层的“分”；标题前后的核心点应与总述中的职责范围一一对应，不能把低信息的“日常工作”“物料产出”单列为主题。
5. **写第二层“总—分”。** 每个主题用一个冒号后的连续段落完成第二层结构：先给核心句，再自然穿插卡点/痛点（有则写）、任务拆解、方法或技术链、协作、交付与结果。标题不计字数，正文严格不少于 80 个可见字符，通常写到 100–180 字；不为凑层级机械标出“问题/方法/结果”。
6. **按需补全但不停笔。** 方法、工具、数据口径或成果细节没写清时，可按该行业一般可行的做法补成完整的“增补草稿”，例如补齐常见的复盘节奏、分析框架、工具类型、交付物或结果观察维度。不要杜撰机构、角色、日期、客户名称、精确数字、专有系统实操或确定性因果结果。增补草稿只在全文末尾保留一次固定提示，不逐项打断正文。
7. **可选 JD 调优。** 有 JD 时只调整主题顺序、术语和展开重点；无 JD 时按业务影响、职责密度和读者理解顺序组织。

## 输出格式

```markdown
## [机构或项目]｜[角色]｜[日期]

**工作概述：** [无第一人称；业务/产品、负责范围、动作目的。源概述不缩短；无源概述时至少 80 个可见字符。]

- **[能力主题一]：** [标题不计字数。核心句后自然展开卡点、行动链、方法/技术链、协作、交付或结果；正文至少 80 个可见字符，优先 100 字以上。]
- **[能力主题二]：** [同上。]
- **[能力主题三]：** [按信息密度保留，可选。]

> 注：数据、方法论、工具等细节需要自行根据事实修正，不保证绝对正确。
```

- 每段固定有一个工作概述与 2–4 个主题；角色或日期未提供时，省略对应标题字段，不补造。
- 主题正文可以在必要时以缩进子项补充，但主要段落仍须独立、连贯、达到长度要求。
- 只要使用了自动补全，全文最后保留上面的固定提示一次；所有内容均来自已给材料时，输出可投递的 `final` 版，不附提示。
- “可见字符”不计 Markdown 标记和主题标题；不设上限。工作概述的最低长度为 `max(80, 源概述可见字符数)`。
- 模式不是给用户增加负担：`enhanced-draft` 用于自动补全后的完整草稿；`final` 用于已按事实核对的版本；`incomplete` 只用于职责与工作动作不足。

## 语言与术语

- 用招聘方熟悉的业务语言翻译陌生组织、模块和缩写；首次出现的必要小众术语补普通含义。
- 以“准确动词 + 对象 + 方法/工具类别 + 交付或观察维度”成句，避免孤立关键词堆砌。
- 区分方法、技术、语言、软件、平台、指标与交付物；例如“编写 SQL 查询”“用 Power BI 搭建看板”“围绕 RICE 排定优先级”，不统称为“工具”。
- 使用自动补全时，优先写可替换的通用工作链和观察维度，而非虚构精确数字或不可回溯的成果。只有“职责与工作内容”不足才停下来要求补充。

## 校验与交付

在输出前计算每段源概述的可见字符数；没有源概述时填 `0`。运行校验器：

```bash
python3 scripts/validate_output.py --mode final output.md
python3 scripts/validate_output.py --mode enhanced-draft output.md
python3 scripts/validate_output.py --mode final --source-overview-lengths 96,0,123 output.md
python3 scripts/validate_output.py --mode incomplete missing-details.md
```

`--source-overview-lengths` 与经历标题顺序一一对应；校验器检查结构、长度、总述第一人称和增补提示，不能自动判断事实是否正确。维护本 Skill 时运行：

```bash
python3 scripts/test_validate_output.py
```
